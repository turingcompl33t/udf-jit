### Notes

UDF Features from SQL ProcBench that we don't currently support:

- Cursor loops - Andy recommends just punting on this, don't spend any time implementing cursors

- Explicit type annotations - e.g. `x :: INT`, not necessary
- Subquery expressions - need to test this out, I remember this failing previously but that was a while back in the implementation

Classes of functions from SQL ProcBench:
- Queries (typically aggregations) that produce a scalar result, and then some imperative computation on these scalar values
- Query-fed `for`-loops
- Query-fed `for`-loops with a query in the loop body
- Integer-fed `for`-loops with a query in the loop body
- Cursor loops

The main takeaway from the meeting today was a new perspective of what we are interested in, from a research perspective. Andy and Todd likely had this in mind the whole time, but somehow I lost sight of this while messing around with the UDF implementation for so long. The point is: we want to identify those aspects of UDFs and their associated SQL queries (both enclosing and embedded) that can be optimized, and the conditions under which this optimization is possible. Specifically, are there cases in which imperative-style optimization that we might be able to pull of in our implementation leads to a better result than the inlining + query optimization applied by Froid and Apfel? This the primary area of research interest now.

### Progress from Last Week

The big effort of last week was a major refactor of the implementation of the pipelines interface in code generation. This implies that I made some big changes that impact every query in the system, not just queries that are embedded in UDFs. The fundamental issue is that the presence of nested pipelines and output callbacks needs to alter the common pipeline code generation interface, and thus far I haven't been able to develop an "elegant" way to express this - the code is relatively difficult to follow because it is now full of conditional statements that determine the bytecode function signatures that should be generated for each pipeline "variant."

I don't want to over-engineer this, and I think that (for now) we can get away with the implementation as it is. However, I would definitely like to revisit this in the future and come up with a more scalable solution.
